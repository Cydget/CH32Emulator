## Work log

- The repository started as a README and a Rust gitignore. No emulator code was present.
- Target chosen for the first machine: CH32V203C8T6. QingKe V4B, RV32IMC, 64 KiB zero-wait flash at `0x08000000` (aliased at `0x00000000`), 20 KiB SRAM at `0x20000000`. Memory map and IRQ numbers taken from `ch32-data` (`CH32V203C8T6.yaml`, `CH32V2_V3.yaml`, `CH32V2_D6.yaml`). TIM2 is IRQ 44.
- Firmware under test uses `ch32-hal` (the Embassy HAL in the ch32-rs org, which consumes `ch32-metapac` generated from `ch32-data`) plus `embassy-executor` and `embassy-time`. The published blink example toggles a GPIO pin. This session's firmware toggles PA15 and increments the SRAM static `BLINK_COUNT`, waiting with `embassy_time::Timer`.
- QingKe startup (`qingke-rt`) copies `.data`, clears `.bss`, writes CSRs `0x800` (gintenr), `0x804` (intsyscr), `0xBC0` (corecfgr), sets `mtvec` to vectored-address mode, and `mret`s into `main`. Interrupt handlers assume the hardware stack pushes caller-saved registers. `mtvec` mode 3 loads the handler address from the vector table.
- The host Rust toolchain and a C linker were not installed. Rust 1.99 and `build-essential` were installed, plus the `riscv32imc-unknown-none-elf` target.
- `qingke` 0.8 refuses to build on this target unless `unsafe-trust-wch-atomics` is enabled, because the target reports byte atomics. The firmware enables that feature.
- Embassy's RISC-V thread executor runs `wfi` inside a critical section. QingKe critical sections clear both MIE and MPIE. The emulator keeps a trap-entry stack of the previous global-enable bit so `mret` still restores it. Without that, the first timer interrupt left the core with interrupts stuck off.
- A headless run of the release ELF for 2,000,000 instructions finished with no faults, PA15 configured as push-pull output, and `BLINK_COUNT` at 5. The web server served the UI and a WebSocket client loaded the same ELF, started the core, and observed `BLINK_COUNT` and PA15.
